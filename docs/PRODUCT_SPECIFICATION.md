# Production Line Dataset

## Полная продуктовая и техническая спецификация

Статус: утверждено владельцем проекта  
Дата: 31 июля 2026 года  
Дата утверждения: 31 июля 2026 года  
Целевой релиз: 1.0  

## 1. Назначение

Production Line Dataset — локальное приложение для предразметки фотографий
производственной линии, ручной проверки результата и формирования датасета для
дальнейшей модели видеоаналитики.

Приложение должно:

1. принимать локальные фотографии;
2. получать предварительную разметку от Codex;
3. проверять формат и геометрию результата;
4. позволять оператору принять, отклонить, повторить или вручную исправить
   разметку;
5. сохранять проверенные координаты;
6. экспортировать подтверждённый YOLO Segmentation-датасет;
7. работать на macOS, Linux и Windows;
8. не допускать бесконечных автоматических повторов и скрытого расхода вызовов
   Codex.

## 2. Главный результат для пользователя

Оператор получает очередь кадров с готовой предразметкой и тратит основное время
на подтверждение результата, а не на редактирование JSON или повторный запуск
всего процесса.

Если автоматическая разметка плохая, оператор может:

- вручную повторить анализ;
- выбрать повтор с детализацией нужной области;
- перейти в графический редактор и полностью разметить кадр самостоятельно;
- увидеть итоговый контур до сохранения;
- получить корректный файл координат без дополнительной обработки.

## 3. Зафиксированные продуктовые решения

### 3.1 Режим распознавания по умолчанию

По умолчанию используется режим `1X`:

- один вызов Codex на кадр;
- автоматический качественный повтор не выполняется;
- оператор сам нажимает «Повторить», если результат его не устраивает;
- технический повтор при невозможности запустить процесс отделён от качественного
  повтора и явно отображается в истории.

### 3.2 Дополнительный режим `2X`

Перед запуском очереди пользователь может выбрать режим `2X`.

В этом режиме:

- первый вызов выполняется всегда;
- второй вызов выполняется только при определённой проверяемой причине;
- общее число автоматических вызовов на один цикл обработки не превышает двух;
- третья автоматическая попытка запрещена;
- ручной повтор остаётся доступным и создаёт новый явно инициированный цикл;
- интерфейс показывает номер попытки, причину второго вызова, длительность и
  итоговый выбранный результат.

`2X` означает максимум два вызова, а не гарантированные два вызова для каждого
кадра.

### 3.3 Фиксированная камера

Глобальная координатная калибровка камеры не используется.

Причины:

- фотографии могут поступать с разных камер;
- ракурсы и положение линии отличаются;
- единый шаблон способен ухудшать разметку.

Класс `line` не размечается и не экспортируется. Существующие настройки
фиксированной камеры должны быть отключены и удалены из рабочего сценария.
Поддержка отдельных профилей камер не входит в релиз 1.0.

### 3.4 Обработка изображения

Запрещены:

- генеративное увеличение;
- дорисовка деталей;
- нейросетевое шумоподавление;
- изменение контраста;
- повышение резкости;
- удаление фона;
- любые преобразования, способные изменить содержимое кадра.

Разрешены:

- чтение оригинала;
- визуальное масштабирование без изменения файла;
- вырезание прямоугольного фрагмента из оригинала;
- передача оригинала и фрагментов в Codex;
- пересчёт координат фрагмента обратно в координаты оригинала.

Оригинальный файл является единственным источником истины и никогда не
перезаписывается.

### 3.5 Локальное обучение

Обучение или дообучение локальной модели не входит в релиз 1.0.

Кнопка «Принять» не обучает Codex. Она только подтверждает аннотацию для экспорта.

## 4. Область релиза 1.0

В релиз входят:

- macOS, Linux и Windows;
- локальный веб-интерфейс;
- очередь и последовательная обработка;
- режимы `1X` и `2X`;
- ручной обычный повтор;
- повтор с детализацией;
- максимум два автоматических вызова;
- история попыток и ревизий разметки;
- графическая ручная разметка;
- сохранение черновика;
- предварительный просмотр итоговых контуров;
- серверная валидация;
- экспорт YOLO Segmentation;
- импорт старой разметки;
- диагностика установки;
- автоматические тесты для всех целевых ОС.

Не входят:

- обучение собственной модели;
- профили фиксированных камер;
- потоковое видео;
- обработка RTSP;
- многопользовательская авторизация;
- облачная база данных;
- параллельная обработка несколькими Codex-процессами;
- генеративное улучшение фотографий;
- автоматическое принятие результата без человека.

## 5. Пользователи

### Оператор разметки

Основной пользователь. Загружает кадры, запускает обработку, проверяет и
исправляет результат.

### Технический специалист

Устанавливает приложение, проверяет Codex CLI, настраивает пути хранения,
диагностирует ошибки и создаёт экспорт.

### Потребитель датасета

Получает ZIP с изображениями, YOLO-файлами, классами и манифестом для обучения
или проверки другой модели.

## 6. Целевые платформы

Релиз имеет четыре явно разделённых варианта запуска:

1. нативная macOS;
2. нативный Linux, включая Ubuntu/Debian, установленный непосредственно на
   компьютер или сервер;
3. нативный Windows 11;
4. Windows 11 + WSL2 как дополнительный способ запуска Linux-версии внутри
   Windows.

WSL2 не требуется для обычной Ubuntu или Debian.

### 6.1 macOS

- macOS 12 или новее;
- Python 3.11 или 3.12;
- установленный и авторизованный Codex CLI;
- Safari, Chrome или Firefox актуальной версии.

### 6.2 Linux

- Ubuntu 20.04+/Debian 10+ как официально поддерживаемая основа;
- Python 3.11 или 3.12;
- установленный и авторизованный Codex CLI;
- Chrome, Chromium или Firefox;
- запуск приложения без графической оболочки допустим, если браузер открывается
  с другой сессии того же компьютера.

### 6.3 Windows

Поддерживаются два сценария:

1. Windows 11 + WSL2 — основной и наиболее предсказуемый вариант;
2. нативный Windows 11 — поддерживаемый приложением вариант при рабочем Codex CLI.

Для нативного Windows требуются:

- Python 3.11 или 3.12;
- PowerShell;
- платформенное управление дочерним процессом Codex;
- пути `.venv\Scripts\...`;
- тестирование на локальном диске NTFS.

SQLite-базу и рабочие каталоги нельзя размещать на сетевом диске или в
синхронизируемой папке во время обработки.

## 7. Кроссплатформенная архитектура процессов

Необходимо выделить интерфейс `ProcessController`.

Он отвечает за:

- запуск Codex без shell-интерпретации;
- передачу аргументов отдельным списком;
- тайм-аут;
- мягкое завершение;
- принудительное завершение;
- завершение дочернего дерева процессов;
- получение stdout, stderr и кода завершения.

Реализации:

- `PosixProcessController` для macOS/Linux:
  `start_new_session`, `SIGTERM`, затем `SIGKILL`;
- `WindowsProcessController`:
  `CREATE_NEW_PROCESS_GROUP`, затем завершение дерева процесса средствами
  Windows и финальный `kill`;
- `FakeProcessController` для тестов.

Бизнес-логика worker не должна напрямую вызывать `os.killpg`.

## 8. Основной пользовательский сценарий

1. Пользователь копирует изображения в `data/incoming`.
2. Нажимает «Сканировать папку».
3. Выбирает режим `1X` или `2X`.
4. Нажимает «Запустить предразметку».
5. Приложение последовательно обрабатывает кадры.
6. Каждый кадр попадает в «На проверке».
7. Пользователь открывает кадр и сравнивает оригинал с наложенной разметкой.
8. Пользователь выполняет одно из действий:
   - «Принять»;
   - «Отклонить»;
   - «Повторить»;
   - «Повторить с детализацией»;
   - «Разметить самостоятельно».
9. После подтверждения кадр становится доступен для экспорта.
10. Пользователь создаёт ZIP только из подтверждённых ревизий.

## 9. Режимы `1X` и `2X`

### 9.1 Выбор режима

Режим выбирается для запуска очереди и сохраняется в записи `run`.

Интерфейс должен показывать:

- `1X · один вызов на кадр`;
- `2X · до двух вызовов при ошибке`;
- короткое предупреждение, что `2X` может увеличить время и расход.

Значение по умолчанию — `1X`.

### 9.2 Причины автоматического второго вызова

Второй вызов в режиме `2X` разрешён для:

- тайм-аута первого вызова;
- ненулевого кода завершения Codex;
- отсутствующего ответа;
- невалидного JSON;
- несоответствия JSON Schema;
- невозможной геометрии;
- запрещённого класса;
- самопересечения полигона;
- нулевой площади;
- точного дубликата объекта;
- причины `blurred_object`;
- причины `uncertain_object_boundary`.

Второй вызов по умолчанию не выполняется для:

- `uncertain_tray_state`;
- `heavy_occlusion`;
- `ambiguous_qr_code`;
- расхождения двух валидных вариантов;
- отсутствия объектов без других признаков ошибки.

Эти случаи сразу передаются человеку, поскольку повтор того же анализа не имеет
надёжного критерия улучшения.

### 9.3 Алгоритм двух попыток

1. Выполнить первый вызов на оригинальном кадре.
2. Проверить технический результат, схему и геометрию.
3. Если результат пригоден — сохранить его и отправить на ручную проверку.
4. Если результат содержит разрешённую причину повтора и включён `2X` —
   подготовить второй вызов.
5. Второй вызов получает оригинал, найденные ошибки и при необходимости
   фрагменты детализации.
6. Проверить второй результат.
7. Выбрать результат по детерминированным правилам.
8. Сохранить обе попытки и причину выбора.
9. Отправить кадр человеку.
10. Никогда не выполнять третью автоматическую попытку.

### 9.4 Выбор результата

Приоритет:

1. валидный результат выше невалидного;
2. результат без технической ошибки выше результата с технической ошибкой;
3. результат без запрещённых классов выше результата с ними;
4. результат с меньшим числом ошибок геометрии выше;
5. результат с меньшим числом причин проверки выше, только если он не потерял
   ранее уверенно найденные объекты;
6. если оба результата валидны, но существенно различаются, автоматический выбор
   запрещён — оператор видит оба варианта и выбирает один;
7. если второй результат хуже, выбранным остаётся первый.

Ни один результат не принимается для экспорта автоматически.

### 9.5 Ручной повтор

Кнопка «Повторить» доступна для `review`, `rejected` и `failed`.

Перед запуском пользователь выбирает:

- обычный повтор на оригинале;
- повтор с детализацией;
- режим этого цикла: `1X` или `2X`.

Ручной повтор создаёт новую ревизию и не удаляет предыдущую.

## 10. Детальный проход по фрагментам

### 10.1 Назначение

Детальный проход нужен, когда объект на полном кадре слишком мал или его граница
определена неуверенно.

Он не улучшает и не перерисовывает фотографию.

### 10.2 Формирование фрагментов

Автоматический фрагмент:

- строится вокруг объекта, отмеченного как требующий детализации;
- использует bbox его полигона;
- получает настраиваемый запас, по умолчанию 20%;
- обрезается границами оригинала;
- сохраняет координаты области в пикселях оригинала;
- не масштабируется и не фильтруется перед сохранением.

Если объект не найден вообще, автоматический объектный crop невозможен. В таком
случае допустимы:

- выбранная пользователем область;
- не более четырёх перекрывающихся плиток оригинального кадра в режиме детального
  повтора.

### 10.3 Ограничения расхода

- один детальный проход является одним вызовом Codex;
- в один вызов передаётся оригинал и не более четырёх фрагментов;
- детальный проход считается второй попыткой в режиме `2X`;
- после него третья автоматическая попытка запрещена;
- интерфейс показывает число переданных изображений, потому что несколько
  изображений могут расходовать больше входных токенов, даже оставаясь одним
  вызовом.

### 10.4 Контракт ответа детального прохода

Каждый фрагмент получает:

- `region_id`;
- `left`, `top`, `right`, `bottom` в пикселях оригинала;
- ширину и высоту фрагмента.

Codex возвращает:

- `region_id`;
- класс;
- полигон в координатах `0..1000` относительно фрагмента;
- признаки видимости и неуверенности.

Приложение самостоятельно и детерминированно переводит точки:

```text
original_x = left + crop_x / 1000 * crop_width
original_y = top  + crop_y / 1000 * crop_height
```

После этого координаты нормализуются относительно полного оригинала.

Codex не отвечает за ручной пересчёт координат между фрагментом и оригиналом.

### 10.5 Объединение результатов

- уверенные объекты первого прохода сохраняются;
- уточнённый объект заменяет соответствующий неуверенный объект;
- дубликаты объединяются по классу и IoU;
- разные классы на почти одинаковой области создают конфликт;
- конфликт никогда не разрешается молча и передаётся оператору;
- итоговый preview строится только на оригинальном кадре.

## 11. Графическая ручная разметка

### 11.1 Вход в редактор

На странице проверки добавляется кнопка «Разметить самостоятельно».

Редактор открывается:

- на той же странице в отдельном полноэкранном режиме;
- с оригинальной фотографией;
- с текущей выбранной ревизией как начальным слоем;
- без изменения исходного изображения.

Пользователь может начать с пустого слоя.

### 11.2 Инструменты

Обязательные инструменты:

- выбор класса;
- добавление четырёхточечного объекта;
- добавление многоугольника от 4 до 20 точек;
- завершение полигона двойным кликом или кнопкой;
- выбор объекта;
- перемещение вершины;
- добавление вершины на ребро;
- удаление вершины;
- перемещение всего объекта;
- изменение класса;
- удаление объекта;
- очистка слоя с подтверждением;
- отмена и повтор действия;
- масштабирование;
- панорамирование;
- полноэкранный режим;
- показ/скрытие подписей;
- показ/скрытие заливки;
- сохранение черновика;
- проверка и сохранение результата.

### 11.3 Горячие клавиши

- `1` — заполненный лоток;
- `2` — QR-код;
- `3` — пустой лоток;
- `Enter` — завершить текущий полигон;
- `Escape` — отменить текущее построение;
- `Delete`/`Backspace` — удалить выбранный объект;
- `Ctrl/Cmd + Z` — отменить;
- `Ctrl/Cmd + Shift + Z` — повторить;
- `+`/`-` — масштаб;
- `0` — вписать изображение;
- `S` — сохранить черновик.

Все действия должны быть доступны и через видимые кнопки.

### 11.4 Координаты

Редактор работает с экранными пикселями, но хранит канонические координаты
`0..1000` относительно оригинала:

```text
normalized_x = round(image_x / image_width * 1000)
normalized_y = round(image_y / image_height * 1000)
```

Масштаб и панорамирование не влияют на сохранённые координаты.

### 11.5 Геометрия ручной разметки

- автоматические аннотации по умолчанию остаются четырёхточечными;
- ручная разметка может содержать 4–20 точек для точного контура;
- полигон не должен пересекать сам себя;
- площадь должна быть больше нуля;
- точки должны находиться в пределах изображения;
- объект не должен содержать одинаковые соседние точки;
- QR по умолчанию создаётся четырьмя точками;
- сервер валидирует ручной результат независимо от браузера.

### 11.6 Сохранение

«Сохранить черновик»:

- сохраняет ревизию;
- не делает её доступной для экспорта;
- позволяет безопасно закрыть страницу.

«Проверить и сохранить»:

- отправляет аннотацию на сервер;
- запускает валидацию;
- пересоздаёт preview;
- пересоздаёт YOLO label;
- делает ревизию выбранной;
- возвращает пользователя в экран проверки.

После этого пользователь отдельно нажимает «Принять».

### 11.7 Контроль результата

До сохранения пользователь видит:

- цветные контуры;
- название класса;
- номер объекта;
- число вершин;
- список геометрических ошибок;
- итоговое количество объектов по классам.

После сохранения preview должен совпадать с редактором с учётом округления
координат.

## 12. Классы и формат датасета

Активные обучаемые классы:

```text
0 — tray_filled
1 — qr_code
2 — tray_empty
```

Семантика классов:

- `tray_filled` — физический лоток, внутри которого непосредственно виден хотя бы
  один достоверно распознаваемый кусок пищевой продукции; цвет без формы и фактуры
  продукции недостаточен;
- `tray_empty` — физический лоток с достаточно видимой внутренней областью без
  пищевой продукции; рука, перчатка или инструмент сами по себе не означают
  заполненность;
- `qr_code` — полностью видимый QR-код, закреплённый только на голове или головном
  уборе работника; QR-коды в других частях сцены не являются целевыми объектами.

Если перекрытие не позволяет достоверно различить пустой и заполненный лоток,
модель не угадывает состояние и направляет кадр человеку с причиной
`uncertain_tray_state`.

`line` является только устаревшим классом старых данных:

- новый Codex-ответ не может его создавать;
- ручной редактор его не показывает;
- preview его не показывает;
- экспорт его не содержит;
- при импорте старых данных он игнорируется;
- внутренний legacy-parser может временно его читать для миграции.

## 24. Итерационный процесс разработки

### 24.1 Обязательный цикл каждой итерации

Работа выполняется последовательно. Параллельный переход к следующей итерации до
завершения текущей запрещён.

Для каждой итерации выполняются шаги:

1. Зафиксировать точный объём итерации.
2. Проверить состояние репозитория и сохранить пользовательские изменения.
3. Реализовать только зафиксированный объём.
4. Добавить или обновить автоматические тесты.
5. Запустить целевые unit/integration/UI-тесты.
6. Запустить полный доступный набор тестов.
7. Выполнить ручной smoke-тест основного сценария итерации.
8. Проверить diff, отсутствие секретов, кадров, базы, логов и временных файлов.
9. Если проверка успешна — создать один атомарный коммит итерации.
10. Отправить коммит в GitHub.
11. Проверить удалённый commit hash и состояние ветки.
12. Сообщить пользователю результат, тесты, ограничения и ссылку на коммит.
13. Только после успешного push перейти к следующей итерации.

Если любой обязательный тест не проходит:

- итерация считается незавершённой;
- push не выполняется;
- проблема исправляется в рамках той же итерации;
- после исправления весь обязательный набор запускается повторно.

Каждая итерация должна оставлять приложение в запускаемом состоянии. Нельзя
пушить промежуточный код, который требует незавершённой следующей итерации для
восстановления основного сценария.

### 24.2 Git-политика итераций

- целевая ветка проекта — `main`;
- одна завершённая итерация соответствует одному логическому коммиту;
- формат сообщения: `Iteration N: краткий результат`;
- push выполняется только после локальной проверки;
- runtime-данные никогда не добавляются в индекс;
- commit hash фиксируется в отчёте по итерации;
- предыдущий commit является точкой безопасного отката;
- изменение утверждённой спецификации выполняется отдельным согласованным
  коммитом.

### Итерация 0. Утверждение спецификации

Результат:

- согласованы режимы `1X/2X`;
- согласован лимит двух автоматических вызовов;
- согласована ручная геометрия 4–20 точек;
- согласованы причины автоматического второго вызова;
- зафиксированы активные классы;
- подтверждены исключённые функции;
- подтверждён порядок итерационной работы.

Проверка:

- пользователь прочитал документ;
- все замечания внесены;
- статус документа изменён на «утверждено»;
- только после явного утверждения спецификация отправляется в GitHub.

### Итерация 1. Кроссплатформенность

Объём:

- выделить `ProcessController`;
- реализовать POSIX и Windows;
- подготовить инструкции `.sh` и `.ps1`;
- исправить тестовые исполняемые файлы;
- добавить CI-матрицу;
- обновить `doctor` и README;
- отключить глобальную калибровку фиксированной камеры.

Проверка:

- unit-тесты POSIX и Windows controller;
- тайм-аут завершает дерево fake-процессов;
- пути с пробелами работают;
- полный fake-runner набор проходит локально;
- GitHub CI проходит на macOS, Ubuntu и Windows;
- ручной запуск подтверждён минимум на текущей macOS;
- инструкции для трёх ОС не содержат абсолютных пользовательских путей.

Push gate:

- приложение продолжает работать на macOS;
- CI зелёный на трёх ОС;
- runtime-данные отсутствуют в commit.

### Итерация 2. Ревизии и миграции

Объём:

- добавить `schema_version`;
- добавить транзакционные миграции;
- мигрировать текущие артефакты;
- добавить `annotation_revisions`;
- добавить selected/approved revision;
- сохранить полную историю без перезаписи.

Проверка:

- новая пустая база создаётся;
- существующая база обновляется без потери кадров;
- одобренные результаты остаются одобренными;
- повтор создаёт новую ревизию;
- экспорт использует approved revision;
- откат тестовой миграции не оставляет частичную схему;
- созданная перед миграцией резервная копия читается.

Push gate:

- миграция протестирована на копии реальной локальной базы;
- число кадров и статусы до/после совпадают;
- текущий экспорт остаётся совместимым.

### Итерация 3. Режимы `1X/2X`

Объём:

- выбор режима запуска;
- автоматический второй вызов по allowlist;
- лимит двух попыток;
- детерминированный выбор;
- история времени и причин;
- интерфейс расхода;
- ручной повтор как отдельный цикл.

Проверка:

- `1X` вызывает runner ровно один раз;
- хороший результат в `2X` вызывает runner один раз;
- retryable-ошибка в `2X` вызывает runner два раза;
- non-retryable-причина не вызывает второй раз;
- третья автоматическая попытка невозможна;
- ручной повтор после завершения создаёт новый цикл;
- обе попытки доступны для просмотра;
- пользователь видит причину и длительность.

Push gate:

- счётчик вызовов подтверждён тестами;
- ни один путь не обходит лимит двух автоматических вызовов;
- старый ручной сценарий «Повторить» сохранён.

### Итерация 4. Детальный проход

Объём:

- `detail_regions`;
- ручной выбор области;
- автоматический crop;
- передача нескольких `--image` в одном вызове;
- локальный пересчёт координат;
- merge объектов и обработка конфликтов.

Проверка:

- байты оригинала до/после совпадают;
- crop соответствует указанному прямоугольнику;
- углы crop правильно переходят в углы оригинала;
- координаты остаются в допустимом диапазоне;
- в вызов передаётся не более четырёх crop;
- детальный вызов учитывается как вторая попытка;
- дубликаты объединяются;
- классовый конфликт отправляется человеку;
- preview строится на оригинале.

Push gate:

- проверка координат выполняется на синтетических изображениях с известными
  точками;
- максимальное число вызовов по-прежнему равно двум;
- преобразование изображения, кроме crop, отсутствует.

### Итерация 5. Графический редактор

Объём:

- canvas/SVG overlay;
- четырёхточечные объекты и полигоны 4–20 точек;
- выбор, перемещение и удаление;
- undo/redo;
- масштаб и панорамирование;
- горячие клавиши;
- черновики;
- серверная валидация;
- preview;
- создание выбранной ручной ревизии.

Проверка:

- можно разметить кадр с нуля без Codex;
- можно исправить автоматическую ревизию;
- масштабирование не изменяет координаты;
- undo/redo не повреждает объект;
- черновик переживает обновление страницы;
- невалидный полигон не становится финальным;
- после сохранения редактор и preview совпадают;
- YOLO label соответствует точкам редактора;
- ручная разметка не расходует вызовы Codex.

Push gate:

- основной ручной сценарий подтверждён E2E-тестом;
- доступна работа мышью и клавиатурой;
- несохранённые изменения защищены предупреждением.

### Итерация 6. Завершение продукта

Объём:

- полный E2E;
- финальная проверка экспорта и legacy;
- документация установки;
- проверка приватности;
- реальный smoke-тест Codex;
- тесты на трёх ОС;
- подготовка релиза 1.0.

Проверка:

- все критерии раздела 25 выполнены;
- CI зелёный;
- ручной сценарий пройден на реальных тестовых кадрах;
- документация воспроизводится на чистой установке;
- публичный репозиторий не содержит runtime-данных;
- известные ограничения перечислены в README.

Push gate:

- финальный commit опубликован;
- GitHub-репозиторий соответствует локальной версии;
- релиз получает версию `1.0.0`.

## 25. Критерии готовности релиза 1.0

Релиз готов, когда:

1. приложение устанавливается по документации на macOS, Ubuntu и Windows 11;
2. все fake-runner тесты проходят на CI-матрице;
3. реальный Codex smoke-тест пройден на macOS, Linux и Windows/WSL2;
4. `1X` никогда не выполняет качественный автоматический повтор;
5. `2X` никогда не превышает два автоматических вызова;
6. пользователь видит причину каждого дополнительного вызова;
7. detail pass не изменяет пиксели исходного файла;
8. координаты фрагментов правильно переносятся на оригинал;
9. ручной редактор позволяет создать, изменить, удалить и проверить объект;
10. ручной черновик переживает обновление страницы;
11. preview соответствует сохранённым координатам;
12. экспорт использует только утверждённую ревизию;
13. line отсутствует в новом датасете;
14. локальные кадры и база не попадают в Git;
15. аварийное завершение не теряет завершённые попытки и черновики;
16. весь основной сценарий подтверждён E2E-тестом.

## 26. Исходное расхождение реализации со спецификацией

На момент создания документа:

- README заявляет только macOS;
- тайм-аут Codex использует POSIX-only `os.killpg`;
- глобальная калибровка фиксированной камеры включена в рабочей конфигурации;
- качественный режим `2X` отсутствует;
- попытки не хранят независимые ревизии аннотаций;
- повтор может перезаписывать текущие артефакты;
- детальный проход отсутствует;
- есть только JSON-редактор;
- ручная графическая разметка отсутствует;
- тесты не выполняются в CI на трёх ОС.

Этот список зафиксировал исходное состояние перед итерациями 1–6. В версии 1.0
пункты устранены; воспроизводимые проверки и платформенные реальные smoke-тесты
описаны в `docs/RELEASE_CHECKLIST.md`.
